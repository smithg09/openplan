RFC: Rate limiting for the public API

A single noisy integration took the API down twice last quarter. This proposes per-key limits, enforced at the gateway, with a clear path for customers who need more.

Problem

Today the only protection is a global concurrency cap. One customer retrying aggressively consumes the whole pool, and every other customer sees 503s. We cannot tell customers what they are allowed to do, so support tickets turn into guesses.

Options considered

OptionAccuracyCostVerdict
Fixed window per keyBursty at window edgesOne counterRejected
Sliding window logExactMemory grows with trafficRejected
Token bucket per keySmooth, allows burstsTwo numbers per keyProposed

Proposal

Each API key gets a token bucket: a steady refill rate and a burst size. Limits live in the gateway; the service behind it is unchanged. Rejected requests return 429 with a Retry-After header.

60 requests / minute
bursts up to 120
HTTP/1.1 429 Too Many Requests
Retry-After: 4
X-RateLimit-Limit: 60
X-RateLimit-Remaining: 0

Open questions

  • Should limits apply per key or per organisation?
  • Do webhooks count against the bucket?
  • How long do we announce the change before enforcing it?
